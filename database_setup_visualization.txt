DATABASE SCHEMA OVERVIEW
========================

shiprag_auth database:
├── users
│   ├── id (UUID PK)
│   ├── email (TEXT UNIQUE)
│   ├── password_hash (TEXT)
│   ├── display_name (TEXT)
│   ├── created_at (TIMESTAMPTZ)
│   └── updated_at (TIMESTAMPTZ)
│
├── api_keys
│   ├── id (UUID PK)
│   ├── user_id (UUID FK → users.id)

│   ├── key_prefix (TEXT)

INDICES & FUNCTIONS
-------------------
- idx_users_email (on users.email)
- idx_api_keys_hash, idx_api_keys_user (on api_keys)
- idx_projects_user, idx_projects_project_id (on projects)
- Multiple indices on chunks for:
  * Vector similarity (ivfflat)
  * Full-text search (gin on content_tsv)
  * Tenant isolation (project_id, project_id+source)
- SQL Functions:
  * match_chunks() - vector-only search
  * match_chunks_hybrid() - vector + keyword search

USAGE FLOW
==========
1. User runs: `shiprag login` → validates against users/api_keys tables
2. User runs: `shiprag init` → creates project in projects table
3. User runs: `shiprag deploy` →
   a. Reads local docs
   b. Chunks + embeds text
   c. Upserts to chunks table via Supabase client
   d. Updates project.chunk_count
4. Query flow:
   a. Frontend sends query to /api/query
   b. Backend embeds query text
   c. Calls match_chunks_hybrid() to find relevant chunks
   d. Returns results to LLM for answer generation
